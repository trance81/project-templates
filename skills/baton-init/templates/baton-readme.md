# Baton — 작업 상태와 수정 이력

## 네 가지 원칙

1. **작업 상태는 `.baton/<이름>/<단위>.md` 한 곳에만 적는다.** 훅이 남기는 기록도
   트랜스크립트도 이 파일보다 높은 권위를 갖지 않는다.
2. **파일은 반복해서 손대는 단위마다 하나다.** 작업마다 새로 만들지 않는다. 같은 단위를
   다시 고치면 같은 파일을 열고, 무엇을 왜 바꿨는지를 수정 이력에 쌓는다.
3. **자기 폴더만 읽고 쓴다.** 다른 사람의 폴더는 사용자가 지시할 때만 연다.
4. **과거 배턴은 git에 영구히 남기되, 컨텍스트에는 필요할 때만 올린다.**

## 이 프로젝트의 배턴 단위

{{BATON_UNIT}}

파일명은 이 단위의 식별자로 짓는다. 날짜나 작업 동사(`-수정`, `-검토`, `-작성`)는 붙이지
않는다. 그런 정보는 파일 안 수정 이력에 들어간다. 식별자 하나로 "이것을 지난번에 어떻게
고쳤나"를 찾을 수 있어야 한다.

## 폴더 구조

```
.baton/
├─ README.md            이 파일 — 규칙                          (git)
├─ <이름>/              사용자별 폴더. 세션 시작 시 자기 것만 읽는다  (git)
│  ├─ <단위>.md         반복 수정 단위별 배턴                    (git)
│  └─ done/             아카이브된 완료 배턴 (선택)              (git)
├─ local/               로컬 전용 메모 + 이 PC의 사용자 이름       (git 제외)
└─ .session/            훅이 쓰는 Stop 거부 횟수                  (git 제외)

scripts/baton-hook.mjs  세션 시작 안내 + 배턴 없는 턴 종료를 막는 훅
```

`<이름>/`은 사용자마다 하나다. 개인 프로젝트라도 이 구조를 그대로 쓴다. 폴더가 하나뿐일
뿐이고, 나중에 팀이 되어도 옮길 것이 없다. 이 PC에서 쓰는 이름은 `.baton/local/owner`에
한 줄로 적어 둔다. 이 파일은 git에 올라가지 않으므로 PC마다 같은 이름을 적어야 한다.

끝난 배턴도 지우지 않는다. 쌓인 파일이 프로젝트의 검색 가능한 수정 이력이 된다.
`resume` 목록이 쌓여서 못 알아보게 되는 문제 대신 내용으로 찾는다.

### 폴더가 여럿일 때

팀 저장소에서는 사람마다 폴더가 하나씩 있으므로 여러 개인 것이 정상이다. 그 자체로는 아무
문제가 아니고 확인할 것도 없다. 판단이 필요한 경우는 `.baton/local/owner`가 없을 때, 즉
이 PC에서 내가 누구인지가 아직 정해지지 않았을 때뿐이다. 그때는 폴더 목록을 사용자에게
보여주고 어느 것이 본인 것인지 묻는다. 폴더가 하나뿐이더라도 그것이 본인 것이라고 가정하지
않는다.

이름이 비슷한 폴더가 여럿 보이더라도(`kwcho`와 `kw-cho`처럼) **스스로 합치지 않는다.** 같은
사람이 PC마다 다른 이름을 썼는지, 아니면 다른 사람인지는 사용자만 판단할 수 있다. 사용자가
명시적으로 합쳐 달라고 할 때에만 다음 순서로 한다.

```
1. 어느 폴더를 어디로 합칠지 사용자에게 확인받는다
2. git 추적 중이면 git mv 로 옮겨 이력을 잇는다
3. 같은 이름의 배턴이 양쪽에 있으면 파일을 지우지 말고 하나로 합친다
   - 수정 이력: 두 파일의 항목을 날짜순으로 섞고 최신이 위로 오게 한다
   - 지금 상태 / 다음 할 일 / 걸린 것: updated 가 더 새로운 쪽만 남긴다
   - status: running 이나 waiting 이 하나라도 있으면 그것을 쓴다
4. 합친 결과를 사용자에게 보여주고 커밋한다
```

## 규칙

1. **프로젝트에 남는 작업을 시작하면** 먼저 자기 폴더에서 그 단위의 배턴을 찾는다.
   있으면 그 파일을 열고 수정 이력을 읽은 뒤 이어 쓴다. `passed`였다면 `running`으로
   되돌린다. 없으면 새로 만든다.
2. **작업이 진전되면 그 파일을 갱신한다.** "지금 상태"와 "다음 할 일"은 덮어쓴다. 매 턴
   갱신하지 않는다. 의미 있는 경계에서만 갱신한다.
3. **작업이 끝나면 수정 이력에 항목을 하나 남기고 `status: passed`로 바꾼다.** 파일은
   지우지 않는다.{{CHANGELOG_LINE}} 커밋을 했다고 해서 배턴을 대신하지 않는다. 커밋은
   "파일이 이렇게 바뀌었다"이고 배턴은 "이 단위를 왜 어떻게 고쳤고 지금 어디까지 왔나"다.
   **닫는 판단은 사용자가 한다.** 작업이 끝났는지 확실하지 않으면 `running`이나 `waiting`으로
   두고 다음 세션이 이어받게 한다. 커밋했다는 사실은 기능이 완료되었다는 뜻이 아니다.
4. **파일 변경이 없어도 결론이 나면 남긴다.** 조사·검토가 "하지 않기로 했다", "확인된
   사실", "우리가 고칠 수 없다" 중 하나로 끝나면 그 결론을 적는다. 아래 "언제 만드나" 참조.
5. **세션 시작 시 읽는 범위는 좁게 유지한다.** 아래 "세션 시작" 참조.

## 언제 만드나

기준은 **소요 턴 수가 아니라 프로젝트에 남는지 여부**다. 한 턴 만에 끝나고 커밋까지 마쳤어도
프로젝트에 남는 변경이면 배턴을 만들거나 갱신한다.

**만들거나 갱신한다**

- 코드·설정 변경 (기능 추가, 버그 수정, 리팩터링, 의존성 교체)
- 이 프로젝트에 속한 문서 작업 (`pjt-docs/` 문서, README, 설계서, 스펙)
- 스키마·인프라·배포 절차 변경
- 파일을 바꾸지 않았어도 결론이 남는 조사. 결론의 성격에 따라 자리가 다르다.
  - **하지 않기로 했다** → `pjt-docs/decisions/`에 결정 문서로. 재론 조건을 함께 적는다.
    관련 단위의 배턴 이력에는 "조사" 항목 한 줄과 그 결정 문서 링크만 남긴다.
  - **확인된 사실** (코드·DB·외부 시스템을 실제로 확인한 결과) → 관련 단위의 배턴 이력에
    "조사" 항목으로. 여러 단위에 걸치는 사실이면 `pjt-docs/domain/`에도 적는다.
  - **우리가 고칠 수 없다** (원인은 알았으나 외부 담당) → `pjt-docs/troubleshooting/`에
    `status: draft`로. 누가 고쳐야 하는지와 문의처를 적는다.

**만들지 않는다**

- 결론 없이 끝난 조사·탐색·일반 질의응답
- 코드 설명, 사용법 질문, 도구 사용법
- 프로젝트와 무관한 대화나 산출물 (다른 프로젝트 이야기, 일회성 스크립트, 개인 메모)
- 되돌릴 것을 전제한 실험이나 임시 확인

**한 배턴은 한 단위다.** 작업 수나 커밋 수와 대응시키지 않는다. 한 단위를 다섯 번 고쳤으면
파일은 하나이고 수정 이력이 다섯 항목이다. 한 작업이 두 단위를 건드렸으면 두 파일에 각각
항목을 남기되, 상태와 다음 할 일은 주가 되는 쪽에만 적고 다른 쪽은 그 파일을 가리킨다.

배턴을 만들지 말지 애매하면 **만든다.** 안 만들어서 잃는 것(수정 이력)이 만들어서 잃는
것(파일 한 장)보다 크다.

## 세션 시작

```
1. 이 README를 확인한다
2. .baton/local/owner 에서 내 이름을 읽는다. 파일이 없으면 사용자에게 묻는다.
   폴더가 하나뿐이어도 그것이 내 것이라고 가정하지 않는다.
3. .baton/<내 이름>/ 최상위의 running / waiting 배턴만 읽는다
4. 진행 중인 배턴이 있으면 새 작업으로 넘어가기 전에 그것부터 사용자와 정리한다
5. done/ 과 passed 는 지금 요청과 관련 있을 때만 검색한다
6. 다른 사람의 폴더는 읽지 않는다. 사용자가 "hong 폴더도 같이 봐줘"처럼
   지시했을 때만 그 파일을 연다
7. local/ 은 필요할 때만 본다. 없어도 작업은 굴러가야 한다
```

`SessionStart` 훅이 1~3을 대신 해서 owner 와 열린 배턴 목록을 세션 첫머리에 넣어 준다. 훅이
걸려 있지 않은 도구에서는 위 순서를 직접 따른다. 어느 쪽이든 **4번은 사람이 판단할 몫이다.**
진행 중인 배턴이 남아 있는데 새 작업을 먼저 시작하면 그 배턴은 계속 열린 채로 쌓인다.

과거 배턴 전부를 매 세션 컨텍스트에 올리면 baton 스스로 컨텍스트를 오염시킨다.
**git에는 영원히 남기고, 컨텍스트에는 필요할 때만 올린다.**

## 파일 형식

```markdown
---
status: running        # 필수. running | waiting | passed
updated: 2026-08-19T14:32:10Z   # 필수. 이 문서를 마지막으로 의미 있게 갱신한 시각(ISO)
host: desk-office       # 선택. 마지막으로 만진 기기
branch: feature/xxx     # 선택. git 있을 때만
---

# <단위 식별자> <사람이 읽을 이름>

## 지금 상태
(덮어쓴다) 현재 어디까지 왔나.

## 다음 할 일
(덮어쓴다) 재개하면 바로 할 것.

## 걸린 것
(덮어쓴다) 막힌 지점, 결정을 기다리는 것.

## 수정 이력
(쌓는다. 최신이 위. 지우지 않는다)

### 2026-08-28 · 결재상신 · Amaranth10 연동으로 교체
- 바꾼 것: `popup()`이 구 그룹웨어 URL 대신 SSO `fullUrl`을 연다
- 이유: 구 Bizbox 그룹웨어 폐기
- 주의: approKey 채번 주체 미확정. 관리자 등록 뒤 재확인

### 2026-08-20 · 조회 · 마감월 필터 추가
- 바꾼 것: 조회 조건에 마감월 콤보 추가, 기본값 당월
- 이유: 현업 요청 (7/20 협의)

### 2026-08-15 · 조사 · 인덱스 추가 여부
- 결론: 하지 않는다. 실행계획상 이득 없음
- 근거: pjt-docs/decisions/0007-사전손익-인덱스.md
```

**필수는 `status`와 `updated` 둘뿐이다.** 나머지 필드는 있으면 좋은 것이고, 필드를 새로
늘리지 않는다. 파일을 열었을 때 사람이 2초 만에 이해되는 게 이 형식의 핵심이다.

**수정 이력 항목의 제목은 `날짜 · 기능 · 요지` 세 토막이다.** 가운데 토막이 이 단위 안의
어느 기능(조회, 저장, 결재상신, 애니메이션 등)을 건드렸는지를 말한다. 파일 안에서 이미 쓴
기능 이름이 있으면 그것을 다시 쓴다. "조회"와 "검색"이 섞이면 나중에 찾을 때 둘 다 봐야 한다.
본문은 바꾼 것, 이유, 주의 세 줄이면 충분하고, 시행착오 과정은 적지 않는다. 결론만 남긴다.

`updated`는 **이 문서를 마지막으로 의미 있게 손댄 시각**이다. 매 턴 찍는 도장과는 쓰임이 다르다.

## 무엇을 적고 무엇을 안 적나

`.baton/<이름>/*.md`는 **git에 올라간다.** 팀이 있으면 팀 전체가, 공개 저장소면 누구나 본다.

**적는다** — 재사용할 정보:

```
접속: ssh prod-web-01   (~/.ssh/config 에 정의된 alias)
키: 1Password "prod-server-ssh" 항목
배포 절차: scripts/deploy.sh 실행 후 nginx reload
```

**안 적는다** — credential 값 자체:

```
password: ...
AWS_SECRET_ACCESS_KEY=...
-----BEGIN PRIVATE KEY-----
```

비밀번호·API 키·토큰·개인키는 값을 쓰지 않는다. **어디에 있는지, 뭐라고 부르는지만** 적는다.
그것만으로 다음 세션이 접속 방법을 알아내는 데 충분하다.

### `local/` — 로컬 전용

기기에만 있는 설정값, 팀에 공유할 수 없는 개인 자료는 `.baton/local/`에 둔다. 같은 파일
형식을 쓰되 git에 올라가지 않는다.

- `local/owner`는 예외적으로 **필수**다. 이 PC에서 쓰는 사용자 이름 한 줄이 들어 있고,
  세션 시작 때 자기 폴더를 찾는 데 쓴다. 지워지면 다음 세션이 이름을 다시 묻는다.
- 나머지는 **참고용이다.** 없어도 작업은 굴러가야 하고, 세션 시작 시 굳이 열어보지 않아도 된다.
- **언제든 지워질 수 있다.** 여기 있는 내용에 의존하는 절차를 만들지 않는다.
- git에 안 올라가므로 **다른 PC에 따라가지 않는다.** 기기마다 다른 값이라 그게 정상이다.
- 여기서도 credential 값은 빼둔다. 로컬 비밀 관리자·`.env`·`~/.ssh/`가 이미 그 일을 한다.

## 훅 — 두 지점에서 거든다

규칙만으로는 지켜지지 않는다. 규칙이 진입 파일에 있고 매 턴 로드되는데도, 컨텍스트가 압축되면
그 규칙이 요약에서 빠진다. 그래서 `scripts/baton-hook.mjs`가 두 지점에서 거든다.

| 지점 | 무엇을 하나 | 결과 |
|---|---|---|
| 세션 시작 (SessionStart) | 이 프로젝트의 baton 구성이 표준보다 뒤처졌으면 알린다. `owner`와 열린 배턴 목록을 세션 첫머리에 넣는다. `owner`가 없으면 폴더 후보를 보여준다. 열린 배턴이 없는데 커밋되지 않은 변경이 있으면 그것도 알린다. 동시에 그 시점의 변경 목록을 기준선으로 남긴다 | 아무것도 막지 않는다 |
| 턴 종료 (Stop) | **이번 세션이** `.baton/` 밖 파일을 새로 바꿨는데, 열린 배턴도 없고 내 배턴 파일도 함께 바뀌지 않았는지 본다 | 턴을 못 끝냄. 세션당 3회까지. 그 뒤엔 경고만 |

**세션이 끝나는 순간을 알려주는 이벤트는 없다.** 창을 닫거나 프로세스가 죽거나 컨텍스트가
넘치면 어떤 훅도 돌지 않는다. 그래서 Stop 은 세션 종료가 아니라 매 턴 끝에 확인한다. 어디에서
끊기더라도 직전 턴까지는 기록되어 있게 하려는 것이다. 턴 도중에 끊겨서 그마저 놓친 경우는
다음 세션의 SessionStart 가 "커밋되지 않은 변경이 있는데 열린 배턴이 없다"로 알려준다. 두
지점이 서로의 빈틈을 메운다.

Stop 은 예방이 아니라 사후 포착이다. 배턴 없이 파일을 여러 개 고치는 것 자체는 막지 못하고,
턴이 끝날 때 붙잡는다. 그 시점에는 방금 한 작업이 아직 컨텍스트에 있으므로 오히려 수정 이력을
제대로 쓸 수 있다.

**판정 기준은 git 작업 트리의 변경이되, 이번 세션이 만든 것만 센다.** SessionStart 가 세션
첫머리의 변경 목록을 기준선으로 적어 두고, Stop 은 그 기준선에 없거나 그보다 새로 바뀐 경로만
본다. 그래서 잡담, 지식 질의, 논의만 하고 끝난 턴에는 배턴을 요구하지 않고, 어제 하다 만
미커밋 변경이 남아 있어도 오늘 질문만 하는 세션이 막히지 않는다. 프로젝트 밖 경로에 만든
산출물과 `.gitignore`된 파일도 `git status`에 잡히지 않으므로 마찬가지다. 반대로 레포 안에
추적되는 임시 산출물을 만들면 배턴을 요구하니, 그런 파일은 프로젝트 밖에 두거나 `.gitignore`에
넣는다.

`.baton/local/owner`가 없으면 Stop 이 막는다. 누구 폴더를 봐야 하는지 모르기 때문이다. 이름을
적고 폴더를 만들면 풀린다. `.baton/` 안쪽만 바뀐 턴은 언제나 통과한다.

git 저장소가 아니면 변경을 감지할 수 없으므로 Stop 은 통과하고 SessionStart 의 안내만 남는다.
프로토타입이라도 원격 없이 `git init`만 해 두면 Stop 이 동작한다. 그러지 않기로 했다면 강제는
없고 세션 시작 안내만 남는데, 관리가 필요 없는 단순한 프로젝트라면 그것으로 충분하다.

훅이 보는 것은 **배턴이 열려 있거나 함께 갱신됐는가**뿐이다. 이력을 남기고 `passed`로 닫은 뒤
커밋 전에 턴을 끝내는 것은 정상이라 막지 않는다. 열린 배턴이 있는 동안에도 조용하다. 이력
항목의 내용이 충실한지, 작업 중간 경계에서 갱신했는지는 훅이 보지 않는다. 그것은 이 문서의
규칙과 그것을 지키는 쪽의 몫이다.

## 표준보다 뒤처졌는지 알아채는 법

훅 스크립트 맨 위에 `BATON_VERSION` 상수가 있다. 이 프로젝트에 복사된 사본은 설치 시점의 값을
그대로 들고 있고, 전역 스킬 폴더(`~/.claude/skills/baton-init/`)의 것은 정본 저장소를 git pull
할 때마다 갱신된다. SessionStart 가 두 값을 비교해서 어긋나면 세션 첫머리에 알린다.

```
[baton] 이 프로젝트의 baton 구성이 표준보다 뒤처져 있습니다 (설치 2026-08-14 / 최신 2026-08-31).
```

이때 "업데이트해" 라고 하면 정본 저장소의 `update.md` 절차로 갱신한다. **갱신은 사용자 승인
뒤에 한다.** 훅 교체와 진입점 규칙 변경이 승인 없이 굴러가면 안 되기 때문이다. 갱신 뒤에는
Claude Code 를 재시작해야 새 훅이 돈다.

전역 스킬이 설치되지 않은 기기에서는 비교할 대상이 없으므로 조용히 넘어간다. 반대로 전역
쪽이 더 낡았으면 정본 저장소를 pull 하라고 알린다.

## `.session/` — 훅의 런타임 기록

세션마다 파일 둘이 들어 있다. `<session>.baseline`은 세션이 시작될 때의 변경 목록이고,
`<session>.guard`는 Stop 을 몇 번 막았는지를 센 값이다. git 미추적이고 사람이 직접 건드리지
않는다. 지워도 다시 만들어지는데, 기준선이 사라진 세션에서는 Stop 이 보수적으로 트리 전체를
보므로 이전 세션이 남긴 변경까지 배턴을 요구할 수 있다.

**관찰하지 못하는 종료가 있다.** 사용자가 중간에 끊거나(Ctrl+C/ESC), 프로세스가 강제로 죽거나,
전원이 나가면 훅 자체가 돌지 않는다. baton 은 이것을 잡으려 하지 않는다. 믿을 것은 배턴 파일
하나이고, 그마저 놓친 경우는 다음 세션의 SessionStart 가 커밋되지 않은 변경으로 알려준다.

## 이 폴더가 커지면

**지우지 않는다.** 이 폴더 자체가 프로젝트의 수정 이력이다.

- `passed` 파일이 쌓여 자기 폴더 최상위가 번잡해지면 `<이름>/done/`으로 옮긴다. 세션 시작 시
  훑는 대상에서만 빠지고, 파일은 살아있고 검색도 된다. 그 단위를 다시 손대면 최상위로 되돌린다.
- 배턴에 쌓인 수정 이력은 그 단위의 기록이므로 배턴에 그대로 둔다. 단위를 넘어 일반화되는
  것(업무 규칙, 아키텍처 결정, 재사용할 절차)만 `pjt-docs/`에 **추가로** 정리한다. 배턴은
  "이것을 언제 왜 어떻게 고쳤나"를, `pjt-docs/`는 "이 프로젝트는 어떻게 돌아가나"를 맡는다.
