# Baton init

`.baton/` 폴더와 턴 종료 훅을 대상 프로젝트에 설치해서, 여러 세션에 걸치는 작업을 사용자가
매번 다시 설명하지 않아도 다음 세션이 이어받게 하고, 같은 단위를 다시 손댈 때 이전에 무엇을
왜 바꿨는지 바로 찾게 한다.

긴 작업은 여러 세션에 걸치는데 세션 사이에 모델은 기억을 유지하지 못하고, `resume` 목록은
쌓일수록 쓸모가 없어진다. 한편 안정화 단계의 화면 하나에는 수십 번의 수정이 쌓이는데, git
이력만으로는 어느 수정이 어느 기능을 왜 건드렸는지 되짚기 어렵다. `.baton/<이름>/<단위>.md`는
모델이 직접 유지하는 작은 Markdown 파일로 이 둘을 함께 맡는다. 상태 절은 덮어쓰고 수정 이력
절은 쌓는다. 규칙만으로는 지켜지지 않는다. 규칙이 진입 파일에 있고 매 턴 로드되는데도, 컨텍스트가 압축되면
그 규칙이 요약에서 빠지고, 배턴을 전부 닫은 뒤 새 작업이 오면 배턴 없이 커밋까지 가는 일이
실제로 있었다. 그래서 훅이 두 지점에서 거든다. 세션을 시작할 때 owner 와 진행 중인 배턴을
보여주고(SessionStart), 변경이 남아 있는데 열린 배턴도 함께 바뀐 배턴도 없으면 턴 종료를
거부한다(Stop). 훅은 모델을 호출하지 않는다. 거부될 때만 모델이 한 턴 더 쓴다.

세션이 끝나는 순간을 알려주는 이벤트는 없다. 창을 닫거나 프로세스가 죽거나 컨텍스트가 넘치면
어떤 훅도 돌지 않는다. 그래서 Stop 은 세션 종료가 아니라 **매 턴 끝**에 확인한다. 어디에서
끊기더라도 직전 턴까지는 이미 기록되어 있게 하려는 것이다. 턴 도중에 끊겨서 그마저 놓친
경우는 다음 세션의 SessionStart 가 "커밋되지 않은 변경이 있는데 열린 배턴이 없다"로 알려준다.
두 지점이 서로의 빈틈을 메운다.

`.baton/` 파일 규약은 도구에 매이지 않는다. 파일을 읽고 쓰는 에이전트라면 자기 진입 파일에
규칙을 적어두는 것만으로 그대로 쓸 수 있다. 도구에 매이는 부분은 훅 **등록**뿐이라서 여기에는
Claude Code 스니펫만 들어 있다. 다른 도구를 쓴다면 설정 형식을 추측하지 말고, 스크립트만
설치한 뒤 그 도구의 어떤 세션 시작·턴 종료 이벤트에 걸어야 하는지 사용자에게 안내하거나 훅을
건너뛴다.

## 절차

대상 프로젝트 루트에서 작업한다. 대화에서 대상이 정해지지 않았다면 현재 작업 폴더를 대상이라고
가정하지 말고 사용자에게 확인한다.

### 1. 이미 있는 것 확인

- `.baton/`이 이미 있으면 신규 설치가 아니라 보수로 다룬다. 기존 배턴 파일의 내용은 덮어쓰지
  않고 빠진 조각(README, 사용자 폴더, 훅, 규칙 줄)만 채운다.
- `.baton/` 최상위에 `README.md` 외의 `.md` 파일이 있으면 **사용자 폴더 이전의 구 구조**다.
  3단계에서 옮긴다. 배턴 파일의 `status` 값이 `running | waiting | passed`가 아니면(예:
  `in-progress | done`) 그것도 구 어휘이므로 함께 처리한다.
- 이 프로젝트가 쓰는 진입 파일을 확인한다. `CLAUDE.md`와 `AGENTS.md`가 흔하고, 이미 있는 것을
  쓴다. 둘 다 있으면 둘 다 손보고, 둘 다 없으면 어느 쪽을 만들지 사용자에게 묻는다.
- 진입 파일에 Baton 규칙 줄이 이미 있으면 5단계를 건너뛴다. 단, 줄의 내용이 아래 5단계의
  것과 다르면(사용자 폴더·수정 이력·착수 전 검색이 빠져 있으면) 구 버전이므로 교체한다.
- `.claude/settings.json`에 Baton 훅이 `SessionStart`·`Stop` 둘 다에 걸려 있으면 7단계를
  건너뛴다. `PreToolUse`나 `StopFailure`에 걸려 있거나 스크립트 이름이 `baton-stop-hook.mjs`면
  구 버전이므로 6·7단계에서 교체하고, 남는 이벤트 항목은 지운다.
- 구 버전은 git pre-commit 도 설치했다. `.git/hooks/pre-commit`(또는 husky 등 프로젝트가 쓰는
  pre-commit 경로)에 `baton-hook.mjs --pre-commit` 호출이 있으면 8단계에서 지운다. 새 훅에는
  그 진입점이 없어서 그대로 두면 커밋할 때마다 오류가 난다.
- git 저장소인지 확인한다. 아니면 8단계에서 `git init`을 권한다.

### 2. 사용자와 단위를 묻는다

두 가지를 묻는다. 둘 다 추측으로 채우지 않는다.

**(a) 이 PC에서 쓸 사용자 이름.** 팀 저장소에서 자기 배턴 폴더를 구분하는 키다. git 계정명,
사번, 별명 어느 것이든 되지만 다른 PC에서도 같은 이름을 써야 하므로 사용자가 늘 쓰는 것을
권한다. 개인 프로젝트여도 묻는다. 폴더가 하나뿐일 뿐 구조는 같다. 답을 `.baton/local/owner`에
한 줄로 쓰고, `.baton/<이름>/` 폴더를 만든다. `.baton/local/`이 없으면 이때 만든다.

`.baton/local/owner`가 이미 있으면 그 값을 보여주고 맞는지만 확인한다. 이미 `.baton/` 아래에
사용자 폴더가 있는데 `owner` 파일이 없으면(다른 PC에서 클론한 경우) 폴더 목록을 보여주고
어느 것이 본인 것인지 묻는다. 폴더가 하나뿐이어도 그것이 본인 것이라고 가정하지 않는다.

팀 저장소에서는 폴더가 여러 개인 것이 정상이므로, 여러 개라는 이유만으로 묻지 않는다. `owner`
파일이 없을 때에만 묻는다. 이름이 비슷한 폴더가 여럿 보여도(`kwcho`와 `kw-cho`처럼) **스스로
합치지 않는다.** 같은 사람이 PC마다 다른 이름을 썼는지는 사용자만 판단할 수 있고, 병합은
파일 이동과 수정 이력 병합을 함께 해야 해서 되돌리기 어렵다. 사용자가 명시적으로 요청할 때에만
어느 폴더를 어디로 합칠지 확인받고 수행한다. 절차는 `.baton/README.md`에 적혀 있다.

**(b) 이 프로젝트에서 반복해서 손대는 단위.** 배턴 파일 하나가 무엇에 대응하는지다. 프로젝트
구조를 보고 후보를 제안하되 결정은 사용자가 한다.

| 프로젝트 성격 | 단위 후보 | 식별자 예 |
|---|---|---|
| 화면 중심 업무 시스템 | 화면·메뉴 | `PSBSOP00400`, `02.06-추가근무결재` |
| 웹사이트·랜딩페이지 | 섹션·페이지 | `hero-section`, `pricing` |
| 미들웨어·배치 | 인터페이스·잡 | `if-eai-103`, `order-sync-job` |
| 분석·설계 | 산출물·주제 | `요구사항정의서`, `부서매핑` |
| 마이그레이션 | 대상 테이블·엔티티 | `mig-기술지원` |
| 라이브러리·도구 | 모듈·명령 | `parser`, `cli-export` |

답을 4단계에서 `{{BATON_UNIT}}` 자리에 넣는다. "이 프로젝트의 배턴 단위는 화면이다. 파일명은
화면 ID(예: `PSBSOP00400`)로 짓는다."처럼 한두 문장이면 된다. 여러 영역이 섞인 프로젝트라면
영역 접두사 규칙(`fe-`, `be-`)도 이 자리에 함께 적는다.

### 3. 구 구조가 있으면 옮긴다

1단계에서 구 구조를 발견했을 때만 한다. 옮기기 전에 무엇을 어떻게 옮길지 목록으로 보여주고
사용자 확인을 받는다.

- `.baton/` 최상위의 배턴 파일을 `.baton/<이름>/`로 옮긴다. git 추적 중이면 `git mv`를 써서
  이력을 잇는다. `done/`이 최상위에 있으면 그것도 `<이름>/done/`으로 옮긴다.
- 배턴이 여러 사람 것이 섞여 있을 수 있다. `assignee` 필드나 파일 내용으로 구분되면 그에 따라
  나누고, 구분할 수 없으면 사용자에게 묻는다.
- `status` 어휘가 다르면 표준으로 바꾼다. 흔한 대응은 `in-progress → running`,
  `done → passed`다. 대응이 분명하지 않은 값은 묻는다.
- 파일명이 날짜 접두사나 작업 동사로 되어 있어도 **이름을 바꾸지 않는다.** 그 파일은 그대로
  두고, 앞으로 만드는 파일부터 단위 식별자를 쓴다. 기존 파일명을 바꾸면 그 파일을 가리키던
  링크와 커밋 메시지가 끊긴다. 사용자가 원하면 바꾸되 스킬이 먼저 제안하지 않는다.
- 기존 배턴의 본문 형식(절 이름, 수정 이력 절 유무)은 손대지 않는다. 다음에 그 파일을 열어
  갱신할 때 자연스럽게 새 형식으로 맞추면 된다.

### 4. `.baton/README.md` 생성

`templates/baton-readme.md`를 읽어 `.baton/README.md`로 쓰되 자리표시자 둘을 치환한다.

- `{{BATON_UNIT}}` — 2단계 (b)의 답.
- `{{CHANGELOG_LINE}}` — 프로젝트에 릴리스나 마일스톤 개념이 있고 체인지로그
  (`CHANGELOG.md`, `pjt-docs/CHANGELOG.md` 등)를 쓰고 있으면 그것을 가리키는 짧은 구절로
  바꾸고(예: " 릴리스에 나갈 변경이면 `pjt-docs/CHANGELOG.md`에도 한 줄 남긴다."), 아니면
  빈 문자열로 바꾼다. 체인지로그는 릴리스·마일스톤 요약 전용이라 매 작업마다 쓰는 것이
  아니다. 없는 관례를 지어내지 않는다.

이미 `.baton/README.md`가 있으면 템플릿과 비교해 빠진 절만 더한다. 특히 "이 프로젝트의 배턴
단위" 절과 "수정 이력" 형식이 없으면 구 버전이므로 사용자 확인 후 통째로 교체한다.

주의할 점이 세 가지 있다.

1. 끝난 배턴은 `status: passed`로 두고 **지우지 않는다.** 수정 이력이 그 파일에 쌓이기
   때문이다. 폴더가 커져서 세션 시작 때 훑기가 부담스러워지면 `passed` 파일을
   `<이름>/done/`으로 옮기고, 삭제하지는 않는다.
2. 문서 메타데이터 예시의 `branch`는 git이 있을 때만 쓰는 필드다. git이 없는 프로젝트라면 뺀다.
3. "무엇을 적고 무엇을 안 적나" 절은 `local/` 하위 절까지 **그대로 남긴다.** 배턴 파일은
   커밋되므로 credential 값을 넣지 않고 어디에 있는지와 무엇이라 부르는지만 적는다는 규칙이
   핵심이다. 분량을 줄이려고 이 절을 쳐내면 규약 자체가 보안 부채로 바뀐다.

### 5. 진입 파일에 규칙 줄 추가

기존 내용 뒤에 덧붙인다. 그 파일의 제목과 목록 스타일에 맞춰 문구를 다듬되 내용은 유지한다.

```
- **IMPORTANT**: 세션 시작 시 `.baton/local/owner`에 적힌 내 폴더(`.baton/<이름>/`)의
  `running`·`waiting` 배턴만 읽고, 진행 중인 것이 있으면 새 작업으로 넘어가기 전에 그것부터
  사용자와 정리한다. `owner`가 없으면 `.baton/` 아래 폴더 목록을 보여주고 어느 것이 본인
  것인지 묻는다. 폴더가 여럿인 것은 정상이며 비슷한 이름을 스스로 합치지 않는다. 다른 사람의
  폴더는 사용자가 지시할 때만 연다. 운영 규칙은 `.baton/README.md`.
- **IMPORTANT**: 프로젝트에 남는 작업을 시작하기 전에 내 폴더에서 그 단위(`.baton/README.md`에
  선언된 단위)의 배턴을 먼저 찾는다. 있으면 수정 이력을 읽고 같은 파일을 이어 쓴다. 없으면
  단위 식별자로 새로 만든다. 날짜나 작업 동사를 파일명에 넣지 않는다.
- **IMPORTANT**: 프로젝트에 남는 작업(코드·설정 변경, 이 프로젝트의 문서 작업)은 한 턴에 끝나
  커밋까지 마쳤더라도 배턴을 갱신하고 수정 이력에 `날짜 · 기능 · 요지` 항목을 남긴 뒤
  `status: passed`로 닫는다. 파일 변경이 없어도 "하지 않기로 했다", "확인된 사실",
  "우리가 고칠 수 없다"로 끝난 조사는 남긴다. 결정은 `pjt-docs/decisions/`에, 사실은 배턴
  이력에, 못 고치는 문제는 `pjt-docs/troubleshooting/`에 draft로. 커밋을 했다고 해서 배턴을
  대신하지 않는다. **닫는 판단은 사용자가 한다** — 끝났는지 확실하지 않으면 `running`이나
  `waiting`으로 두고 다음 세션이 이어받게 한다. 커밋은 기능 완료가 아니다.
```

읽는 범위, 찾는 순서, 남기는 기준을 모두 이 줄에 담고 `.baton/README.md`로 미루지 않는다.
진입 파일은 매 세션 로드되지만 폴더 README는 한 걸음 뒤에, 그것도 읽힐 때만 읽히기 때문이다.
실제로 자주 나는 실수 넷이 있다. 폴더 전체를 읽어 컨텍스트를 낭비하는 것, 같은 화면을 고치면서
지난 배턴을 안 찾고 새 파일을 만드는 것, 한 턴 만에 고치고 커밋까지 끝낸 작업을 "끝난 일"로
보고 이력을 안 남기는 것, 그리고 요청받은 수정을 마쳤다는 이유로 사용자에게 묻지 않고 배턴을
`passed`로 닫아 버리는 것이다. 세 줄이 그 넷을 막는다. 이유를 함께 적는 것도 수정의
일부인데, 이유가 붙은 규칙이 맨 지시보다 오래 지켜지기 때문이다.

### 6. 훅 스크립트 설치

`templates/baton-hook.mjs`를 `<프로젝트 루트>/scripts/baton-hook.mjs`로 복사한다. `scripts/`
폴더가 없으면 만든다. 프로젝트가 훅 스크립트를 다른 곳에 모아둔다면 그 위치에 두고 7단계의
경로를 맞춘다. 프로젝트별 값이 들어 있지 않아서 그대로 복사하면 되고, 실행 시점에 자기 `cwd`
위쪽 어딘가에 `.baton/`만 있으면 동작한다. 구 버전 `scripts/baton-stop-hook.mjs`가 있으면
지우고 이것으로 바꾼다.

스크립트 하나가 두 가지 일을 한다.

| 지점 | 조건 | 동작 |
|---|---|---|
| `SessionStart` | 언제나 | exit 0. 이 프로젝트의 baton 구성이 표준보다 뒤처졌으면 먼저 알린다. `owner`와 열린 배턴 목록을 알린다. `owner`가 없으면 `.baton/` 아래 폴더를 후보로 보여주고 묻게 한다. 열린 배턴이 없는데 커밋되지 않은 변경이 있으면 그것도 알린다. 동시에 그 시점의 변경 목록을 `.session/<id>.baseline`에 기준선으로 남긴다 |
| `Stop` | **이번 세션이** `.baton/` 밖 파일을 새로 바꿨는데, 열린 배턴도 없고 `.baton/<이름>/` 배턴 파일도 함께 바뀌지 않았다 | exit 2. 턴 종료 거부. 세션당 3회까지, 그 뒤엔 경고만 남기고 통과 |

**판정 기준은 git 작업 트리의 변경이되, 이번 세션이 만든 것만 센다.** SessionStart 가 세션
첫머리의 변경 목록을 경로별 수정 시각과 함께 기준선으로 적어 두고, Stop 은 그 기준선에 없거나
그보다 새로 바뀐 경로만 본다. 그래서 잡담, 지식 질의, 논의만 하고 끝난 턴에는 배턴을 요구하지
않고, **이전 세션이 남긴 미커밋 변경 때문에 파일을 건드리지 않은 턴이 거부되지도 않는다.**
이 기준선이 없으면 어제 하다 만 변경이 남아 있는 저장소에서 질문 한 번 하는 세션까지 막힌다.
기준선 파일이 없는 세션(훅을 도중에 걸었거나 다른 도구로 시작한 경우)에서는 보수적으로 트리
전체를 본다. 프로젝트 밖 경로(스크래치 폴더 등)에 만든 산출물과 `.gitignore`된 파일은
`git status`에 잡히지 않으므로 어느 경우에도 조용하다. 반대로 레포 안에 추적되는 임시 산출물을 만들면 배턴을 요구하니, 그런 파일은
프로젝트 밖에 두거나 `.gitignore`에 넣도록 사용자에게 안내한다.

`.baton/local/owner`가 없으면 Stop 이 막는다. 누구 폴더를 봐야 하는지 모르기 때문이다.
`.baton/` 안쪽만 바뀐 턴은 통과한다. 그래야 `owner`와 배턴을 만들 수 있다.

git 저장소가 아니면 변경을 감지할 수 없으므로 Stop 은 통과하고 SessionStart 의 안내만 남는다.
그래서 8단계에서 `git init`을 권한다.

### 7. Claude Code 훅 등록

`templates/settings-snippet.json`을 `.claude/settings.json`에 병합한다. 파일이 없으면 스니펫
내용으로 새로 만들고, 있으면 `SessionStart`와 `Stop` 배열에 각각 **덧붙인다.** 먼저 읽어서
이미 있는 다른 훅을 덮어쓰지 않도록 한다. `SessionStart`에는 다른 도구의 훅이 이미 걸려 있는
경우가 많으므로 특히 주의한다. 6단계에서 기본 위치를 쓰지 않았다면 스크립트 경로를 고친다.
구 버전 항목(`baton-stop-hook.mjs`를 가리키는 것, `PreToolUse`에 걸린 것, `StopFailure`에
걸린 것)이 있으면 지운다. 새 스크립트는 그 세 이벤트를 처리하지 않는다.

Claude Code는 훅 설정을 세션 시작 때 읽어 두고 그 세션 동안 그것을 쓴다. 지금 세션에서
settings.json을 바꿔도 새 훅은 다음 세션부터 돌고, 구 스크립트를 지웠다면 지금 세션은 턴이
끝날 때마다 그 파일을 못 찾는다는 non-blocking 오류를 낸다. 작업에는 영향이 없다. 10단계에서
재시작하라고 알린다.

`SessionStart`는 `systemMessage`와 `hookSpecificOutput.additionalContext`를 함께 담은 JSON 을
내보낸다. **평문을 stdout 에 쓰면 모델 컨텍스트로만 들어가고 사람 화면에는 보이지 않는다.**
세션을 연 사람이 진행 중인 배턴을 눈으로 바로 확인하려면 `systemMessage`가 있어야 하고,
모델이 그 맥락을 들고 첫 턴을 시작하려면 `additionalContext`가 있어야 한다. 둘 중 하나만
남기면 절반이 사라지므로 형식을 바꾸지 않는다.

다만 화면에 보이는 것과 모델이 먼저 말을 꺼내는 것은 다르다. 목록은 세션을 열자마자 배너에
찍히지만, 모델은 사용자 입력이 있어야 턴을 시작한다. 입력 없이 모델이 먼저 발화하게 하는
방법은 없다.

`SessionStart`의 `matcher`는 빈 문자열이라 `startup`뿐 아니라 `resume`·`clear`·`compact`에도
걸린다. 특히 `compact`가 중요하다. 컨텍스트가 압축되면 진입 파일의 규칙이 요약에서 빠지는데,
이때 열린 배턴 목록이 다시 들어와야 압축 이후의 턴이 배턴을 잊지 않는다.

스니펫의 `${CLAUDE_PROJECT_DIR}`는 도구가 알아서 확장하므로 그대로 둔다. `command`는 문자열
하나이며 `args` 배열을 받지 않는다. 경로에 공백이 있어도 깨지지 않도록 안쪽에 큰따옴표를
둘렀으니(`node \"${CLAUDE_PROJECT_DIR}/scripts/baton-hook.mjs\"`) 그 형태를 유지한다.

### 8. git 저장소 확인

배턴 파일이 다른 PC와 팀원에게 넘어가려면 git 이 있어야 하고, Stop 훅도 `git status`로
판정한다. 그래서 git 저장소인지를 여기에서 확인한다.

- **git 저장소면** 아무것도 하지 않는다.
- **아니면 원격 없이 `git init`만이라도 하도록 권한다.** 프로토타입이나 초기 버전이라도
  되돌릴 지점이 필요하다는 점, 그리고 배턴의 수정 이력이 git 없이는 이 PC 밖으로 나가지
  못한다는 점을 함께 알린다. 사용자가 실행을 승인하면 `git init`을 하고, 원치 않으면
  강제 없이 진행한다. 그 경우 Stop 훅은 통과만 하고 SessionStart 의 안내만 남는다는 것을
  결과 보고에 밝힌다. 관리가 필요 없는 단순한 프로젝트라면 그것으로 충분하다.
- 구 버전이 설치한 `.git/hooks/pre-commit`(또는 husky 등의 pre-commit 설정)에
  `baton-hook.mjs --pre-commit` 호출이 있으면 그 줄을 지운다. 새 스크립트에는 그 진입점이
  없어서 그대로 두면 커밋할 때마다 오류가 난다. 그 줄만 지우고 파일의 나머지는 손대지 않으며,
  파일에 그 줄밖에 없으면 파일째 지운다.

### 9. 기기별 로컬 폴더를 git에서 제외하고, 배턴은 git에 넣는다

`.gitignore`에 아래 두 줄이 없으면 추가한다.

```
.baton/.session/
.baton/local/
```

`.session/`은 훅이 쓰는 런타임 정보(Stop 거부 횟수)를 담고, `local/`은 이 PC의
사용자 이름과 팀에 넘길 수 없는 기기 로컬 값을 두는 자리다. 둘 다 git으로 관리할 대상이
아니고 기기 사이에서 병합되지도 않는다.

반대로 **`.baton/<이름>/`은 반드시 git에 들어가야 한다.** 수정 이력이 이 파일에 쌓이므로
버전관리 밖에 두면 다른 PC와 팀원에게 보이지 않아 규약의 목적이 사라진다. `.baton/`이
`.gitignore`나 `.git/info/exclude`에 통째로 올라 있으면 사용자에게 알리고 제외를 푼다.
pjt-docs가 소스와 별개의 독립 저장소인 구성이라면 `.baton/`도 그 저장소 안에 둔다. 폴더가
다르므로 확정 지식과 진행 상태가 섞이지 않는다.

### 10. 결과 보고

새로 만든 파일과 이미 있어서 손대지 않은 파일을 구분해서 알리고, 사용자 이름과 배턴 단위를
무엇으로 정했는지, 어떤 진입 파일을 썼는지, 두 훅(SessionStart·Stop)을 각각 걸었는지
(건너뛰었다면 그 이유를), 구 구조를 옮겼다면 무엇을 어디로 옮겼는지 밝힌다. git 저장소가
아닌 채로 진행했다면 Stop 훅이 동작하지 않는다는 점을 다시 알린다. 구 버전의 pre-commit 을
지웠다면 그것도 밝힌다.

`.baton/local/owner`는 git 에 올라가지 않으므로 **다른 PC에서 클론하면 그 PC에서 다시 만들어야
한다**고 알린다. 그 전까지 세션 시작 때마다 이름을 묻고 Stop 이 막는다. 이것은 의도된
동작이며 사용자가 손으로 관리한다.

훅 설정을 바꿨거나 구 스크립트를 지웠다면 **Claude Code를 재시작해야 새 훅이 돈다**고 알린다.
재시작 전까지 턴이 끝날 때마다 구 스크립트를 못 찾는다는 오류가 보일 수 있는데 무해하다.
이 프로젝트에서 다른 에이전트도 쓴다면 `.baton/` 파일 규약은 그쪽에서도 그대로 동작하며,
그 에이전트의 진입 파일에 규칙 줄만 추가하면 된다. 다만 훅은 그 도구의 세션 시작·턴 종료
이벤트에 같은 스크립트를 걸어야 돌아간다.

Claude Code 훅은 실제 턴 밖에서 발동시킬 방법이 없으므로 스모크 테스트는 하지 않는다. 파일이
있는지와 훅 설정이 파싱되는지만 확인한다.

## 참고

`templates/` 폴더에 이 스킬이 쓰는 파일이 있다.

- `baton-readme.md`: `.baton/README.md` 내용이며, 자리표시자는 `{{BATON_UNIT}}`과
  `{{CHANGELOG_LINE}}` 둘이다.
- `baton-hook.mjs`: `SessionStart`와 `Stop`이 공용으로 쓰는 스크립트이며 자리표시자가 없다.
  맨 위의 `BATON_VERSION` 상수가 이 스크립트의 판이며 `STRUCTURE.md`의 "표준 갱신일"과 같은
  값을 쓴다. **표준 갱신일을 올릴 때 이 값도 함께 올린다.** 두 값이 어긋나면 뒤처짐 알림이
  엉뚱한 시점에 뜨거나 아예 안 뜬다.
- `settings-snippet.json`: `.claude/settings.json`에 병합할 Claude Code 훅 설정이다.
