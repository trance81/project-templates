# Baton — 세션을 넘는 작업 상태

## 네 가지 원칙

1. **`.baton/<slug>.md`가 작업 상태의 유일한 정본이다.** 사이드카도 트랜스크립트도
   이 파일보다 높은 권위를 갖지 않는다.
2. **모든 턴을 기록하지 않는다.** 다음 세션에 필요한 상태만 적는다.
3. **사이드카는 로컬 복구 단서일 뿐이다.** 세션이 이상하게 끝났을 때 참고한다.
4. **과거 배턴은 git에 영구히 남기되, 컨텍스트에는 필요할 때만 올린다.**

## 폴더 구조

```
.baton/
├─ README.md        이 파일 — 규칙                    (git)
├─ <slug>.md        작업·기능 단위 배턴                (git)
├─ done/            아카이브된 완료 배턴 (선택)         (git)
├─ local/           로컬 전용 메모 (선택)              (git 제외)
└─ .session/        훅이 쓰는 런타임 기록              (git 제외)
```

끝난 작업도 지우지 않는다. 쌓인 파일이 프로젝트의 검색 가능한 작업 인덱스가 된다 —
`resume` 목록이 쌓여서 못 알아보게 되는 문제 대신 내용으로 찾는다.

## 규칙

1. **여러 세션에 걸칠 작업을 시작하면** `<slug>.md`를 만든다. 파일명은 관련 브랜치 이름과
   맞추면 대응이 눈에 보인다. 즉시 끝나는 작업(오타 수정 등)에는 만들지 않는다.
2. **작업이 진전되면 그 파일을 갱신한다.** 새 파일을 만들지 않는다. 매 턴 갱신하지 않는다 —
   의미 있는 경계에서만. 중간 시행착오는 적지 않는다(git 이력에 있다).
3. **작업이 끝나면 `status: passed`로 바꾸고 파일은 남긴다.** 지우지 않는다.{{CHANGELOG_LINE}}
4. **세션 시작 시 읽는 범위는 좁게 유지한다** — 아래 참고.

## 세션 시작

```
1. 이 README를 확인한다
2. .baton/ 최상위의 running / waiting 배턴만 읽는다
3. done/ 과 passed 는 지금 요청과 관련 있을 때만 검색한다
4. local/ 은 필요할 때만 본다 — 없어도 작업은 굴러가야 한다
```

과거 배턴 전부를 매 세션 컨텍스트에 올리면 baton 스스로 컨텍스트를 오염시킨다.
**git에는 영원히 남기고, 컨텍스트에는 필요할 때만 올린다.**

## 파일 형식

```markdown
---
status: running        # 필수. running | waiting | passed
updated: 2026-08-19T14:32:10Z   # 필수. 이 문서를 마지막으로 의미 있게 갱신한 시각(ISO)
host: desk-office       # 선택. 마지막으로 만진 기기
branch: feature/xxx     # 선택. git 있을 때만
assignee: hong           # 선택. 여러 명이 이 폴더를 같이 쓸 때만
session: <session-id>   # 선택. 사이드카를 빨리 찾기 위한 힌트일 뿐 —
                         # 모델이 자기 세션 ID를 늘 아는 건 아니라서 낡을 수 있다.
                         # 복구 절차가 이 값에 의존하면 안 된다.
---

# 제목

## 지금 상태
...

## 다음 할 일
...

## 왜 이 방향
(선택) 버린 선택지 + 한 줄 이유. 서술형으로 늘리지 않는다.

## 완료 조건
(선택) 검증 가능한 기준만.

## 걸린 것
...
```

**필수는 `status`와 `updated` 둘뿐이다.** 나머지는 있으면 좋은 것. 필드를 새로 늘리지 않는다 —
파일을 열었을 때 사람이 2초 만에 이해되는 게 이 형식의 핵심이다.

`updated`는 **이 문서를 마지막으로 의미 있게 손댄 시각**이다. 매 턴 찍는 도장과는 쓰임이 다르다.

## 무엇을 적고 무엇을 안 적나

`.baton/*.md`는 **git에 올라간다.** 팀이 있으면 팀 전체가, 공개 저장소면 누구나 본다.

**적는다** — 재사용할 정보:

```
접속: ssh prod-web-01   (~/.ssh/config 에 정의된 alias)
키: 1Password "prod-server-ssh" 항목
배포 절차: scripts/deploy.sh 실행 후 nginx reload
```

**안 적는다** — credential 값 자체:

```
password: ...
AWS_SECRET_ACCESS_KEY=...
-----BEGIN PRIVATE KEY-----
```

비밀번호·API 키·토큰·개인키는 값을 쓰지 않는다. **어디에 있는지, 뭐라고 부르는지만** 적는다.
그것만으로 다음 세션이 접속 방법을 알아내는 데 충분하다.

### `local/` — 로컬 전용 메모

기기에만 있는 설정값, 팀에 공유할 수 없는 개인 자료는 `.baton/local/`에 둔다. 같은 파일
형식을 쓰되 git에 올라가지 않는다.

- **참고용이다.** 없어도 작업은 굴러가야 하고, 세션 시작 시 굳이 열어보지 않아도 된다.
- **언제든 지워질 수 있다.** 작업 도중이든 완료 후든. 여기 있는 내용에 의존하는 절차를
  만들지 않는다.
- git에 안 올라가므로 **다른 PC에 따라가지 않는다.** 기기마다 다른 값이라 그게 정상이다.
- 여기서도 credential 값은 빼둔다. 로컬 비밀 관리자·`.env`·`~/.ssh/`가 이미 그 일을 한다.

## 사이드카 (`.session/`)

훅이 쓰는 런타임 기록이다. git 미추적, 사람이 직접 건드리지 않는다.

```json
{ "observedAt": "...", "event": "Stop", "transcriptPath": "...", "lastMessage": "..." }
```

`observedAt`은 **훅이 이 세션을 마지막으로 관찰한 시각**이다. 배턴이 최신인지까지는 말해주지 않는다.
턴이 API 오류로 끝났으면 `event`가 `StopFailure`가 되고 `error`가 함께 실린다.

**사이드카는 배턴 문서의 신선도를 증명하지 않는다.** 마지막으로 관찰된 세션 상태를 남겨서,
배턴 내용이 의심스럽거나 세션이 비정상적으로 끝났을 때 복구 단서로 쓴다.

쓰는 법:

```
1. running / waiting 배턴을 읽는다
2. 배턴이 미심쩍으면 .session/ 에서 observedAt 이 가장 최근인 파일을 본다
   (배턴에 session 필드가 있으면 그걸로 바로 찾아도 된다 — 다만 낡아 있을 수 있다)
3. 사이드카의 마지막 응답이 배턴 내용과 의미 있게 다르면
   transcriptPath 를 확인하고 배턴을 보정한다
```

`observedAt`이 `updated`보다 새로운 것은 **작업 중에는 정상**이다 — 본문은 경계에서만 쓰니까.
참고할 가치가 생기는 건 그 세션이 끝난 뒤, 마지막 턴으로부터 충분한 시간(예: 5분)이 지났는데도
본문이 그대로일 때다. 그때조차 사람이 열어보고 판단한다.

**관찰하지 못하는 종료가 있다.** 사용자가 중간에 끊거나(Ctrl+C/ESC), 프로세스가 강제로
죽거나, 전원이 나가면 훅 자체가 돌지 않는다. baton은 이걸 잡으려 하지 않는다 — 정본은
어차피 `.baton/*.md`이고, 사이드카는 최선을 다한 단서일 뿐이다.

## 이 폴더가 커지면

**지우지 않는다** — 이 폴더 자체가 프로젝트의 작업 인덱스다.

- `passed` 파일이 쌓여 최상위가 번잡해지면 `.baton/done/`으로 옮긴다. 세션 시작 시 훑는
  대상에서만 빠지고, 파일은 살아있고 검색도 된다.
- 재사용 가치 있는 지식(설정 절차, 결정 근거)은 프로젝트 지식베이스나 `CLAUDE.md`/`AGENTS.md`에
  **복사**해 둔다. 배턴은 그대로 두고 사본만 옮긴다 — 지식베이스는 "왜 이렇게 결정했나"를
  정리된 형태로, 배턴은 "이 작업이 어디까지 갔나"를 작업 단위로 남긴다.
  시간순 변경 이력은 git log의 몫이다 — 배턴 본문은 덮어쓰기 때문이다.
